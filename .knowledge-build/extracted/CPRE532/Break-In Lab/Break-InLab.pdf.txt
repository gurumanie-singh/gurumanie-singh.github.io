Break-In Lab Writeup 
Gurumanie Singh Dhiman 
VM IP Address (IPv4): 190.100.60.238/24 
Executive Summary 
For this Break-In Lab, I conducted a penetration test against the 532Corp network for the 
IP range 82.46.91.0/24. After doing so, I uncovered multiple critical and high-severity 
vulnerabilities across nine machines, including unencrypted Telnet services with weak 
credentials, SQL injection vulnerabilities on web login pages, DNS zone transfer 
misconfiguration exposing internal network topology, anonymous LDAP access, password 
reuse across systems, a backdoor account with unrestricted sudo access, and an 
unencrypted MySQL database containing sensitive employee PII. I was able to gain 
successful access to multiple machines using credential brute-forcing techniques from 
OSINT reconnaissance of the 532Corp public-facing website.

Strategic Recommendations 
1. Disable Telnet and instead replace it with SSH 
Since telnet transmits data including passwords in plain text. All Telnet services (port 23) 
should be disabled immediately and replaced with SSH.  
2. Enforce Strong Password Policies 
Two accounts were compromised using passwords that were directly from publicly 
available employee biographical information. Passwords must not reference personal 
information. Implement a minimum complexity policy or multi-factor authentication. 
3. Remediate SQL Injection Vulnerabilities 
Both .201 and .206 are vulnerable to SQL injection on /login.php. All database queries must 
use parameterized statements or prepared statements. Input validation and output 
encoding must be implemented.  
4. Restrict DNS Zone Transfers 
DNS zone transfers should be restricted to authorized secondary DNS servers only using 
ACLs in the BIND configuration (allow-transfer directive). Zone transfers to arbitrary hosts 
expose the full internal network topology. 
5. Remove Backdoor Accounts and Audit sudo Permissions 
The 'backdoor' account on .204 with unrestricted sudo privileges constitutes a critical 
vulnerability. All user accounts must be audited. The /etc/sudoers file should follow the 
principle of least privilege. The 'sarah' account with passwordless su access must be 
removed or secured. 
6. Encrypt Sensitive Database Contents 
Employee PII (SSNs, credit card numbers) stored in the MySQL database on .206 must be 
encrypted at rest using AES-256 or equivalent. Access to the database should require 
authentication and be restricted to authorized application accounts only.

7. Disable Anonymous LDAP Bind 
The LDAP server on .205 allows anonymous binding, exposing directory structure. 
Anonymous access should be disabled. All LDAP queries should require authenticated 
credentials, and access to sensitive attributes should be restricted by ACL. 
8. Remove LDAP Account Manager from Public Web 
The /lam/ endpoint (LDAP Account Manager) is accessible on port 80 without 
authentication challenges. This web interface should be removed from public-facing 
Apache or placed behind VPN/IP restriction. 
Conclusion 
This penetration test revealed a network with many critical vulnerabilities across multiple 
machines. The most impactful attack chain began with passive OSINT reconnaissance of the 
532Corp public website, which got me employee biographical details that were then used 
to construct a targeted password wordlist. This wordlist enabled me to brute-force access 
to the LDAP server via unencrypted Telnet, which in turn revealed a hidden internal 
network message pointing to a secret machine only accessible from inside the network. 
Additional critical findings include things such as the SQL injection vulnerabilities on two 
machines allowing authentication bypass, a DNS zone transfer misconfiguration exposing 
the entire internal IP topology, a backdoor account with unrestricted root access via sudo, 
and an unencrypted database containing sensitive employee PII.
