Question: How do the specifications (e.g., CPU, memory) of the eNB and UE containers influence network 
performance? What security considerations should be kept in mind when configuring these resources? 
Higher CPU allocation (6 cores) allows the containers to process radio signals and protocol stacks faster, which then 
reduces latency. More memory (8192 MB) supports larger data buffers which prevents packet drops under heavy 
load. Security considerations would include things like using strong passwords for root access, not exposing 
container ports to the public internet, or possibly avoiding default credentials since these containers run real radio 
software that could be exploited if left open.

Question: Why is it crucial to start the EPC before the eNB? How does the interaction between these components 
affect the overall network functionality? 
The EPC needs to start first so that the eNB can register with the EPC using the S1 interface before it can serve any 
of the UEs. If the eNB starts without a running EPC, it basically has nowhere to send the S1 Setup Request and will 
fail. The EPC handles auth, IP allocation, and session management and without it the eNB can’t authenticate users 
or route the data.

What indicates saturation? 
Saturation is indicated by the packet loss steadily increasing (22% to 39% to 48%) while the server-side

How does adjusting the bandwidth allocation affect throughput and latency? 
Below the saturation point (roughly 20M), throughput scales with the requested bandwidth. Above it, the 
throughput stops improving but packet loss increases and the jitter gets worse, which increases the effective 
latency. The network cannot deliver more than approximately 16 Mbps on this link.

Document the TCP throughput and compare with your UDP results. Why might they differ? 
TCP achieved about 16.9 Mbps, which is very similar to UDP. However, TCP handles errors through 
retransmissions rather than just dropping packets. This means TCP throughput is more consistent but can vary 
more over time as it adjusts its congestion window. UDP at 25M showed 39% packet loss, while TCP 
automatically slows down before that happens. The slightly lower TCP throughput compared to UDP's client-
side rate is expected because TCP has additional overhead from acknowledgment packets and connection 
management.

Running both directions at the same time reduces the available resources for each individual direction. The 
uplink dropped to 15.7 Mbps (with 24% packet loss) compared to around 16 Mbps unidirectional, and the 
downlink was 18.8 Mbps. Each direction had more packet loss than in the unidirectional tests. 
• 
Is the total bidirectional throughput equal to the sum of unidirectional tests? Explain. 
No, not exactly. The unidirectional UDP test at 20M target gave about 16.2 Mbps in one direction. If the link 
were perfectly symmetrical and fully separated, bidirectional would be 2 × 16.2 = 32.4 Mbps. The actual total 
was roughly 34.5 Mbps, which is slightly higher because LTE uses FDD (Frequency Division Duplex) where the 
uplink and downlink operate on separate frequencies simultaneously. However, both directions still share the 
same hardware and processing resources, so there is some interference and each direction performs slightly 
worse than in isolation.

Analysis:

Discuss the effect distance has on throughput in a 4G network. 
In a 4G network, as the UE moves farther from the eNB, the received signal power (RSRP) decreases and the 
signal-to-noise ratio (SNR) worsens. This causes the eNB to assign lower-order modulation schemes (lower 
MCS values), which reduces the data rate. Path loss increases with distance, meaning more signal energy is lost 
before reaching the receiver. 
• 
Describe the changes you observed based on change in throughput. 
Host 009 was at a moderate distance and showed stable performance around 15.7 Mbps with RSRP=−79 dBm 
and SNR=19–20 dB. For host 020, the iperf client-side showed roughly 20.4 Mbps but a datagram 
acknowledgment warning appeared, suggesting some link instability. Without a full console trace for host 020, 
exact signal metrics could not be compared directly. 
• 
Comment on the link quality based on metrics such as RSRP, RSRQ, SNR, CFO if visible. 
For host 009, RSRP of −79 dBm is a moderate signal level (acceptable for LTE; strong is above −80 dBm). SNR of 
19–20 dB is a healthy value supporting higher-order modulation. CFO of −350 Hz is a small carrier frequency 
offset that the system corrects automatically. If a farther host showed lower RSRP and SNR, you would expect 
higher BLER (block error rate) and lower brate in the console trace.
