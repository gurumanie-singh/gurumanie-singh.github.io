Lab Experiment #3 – UDP Socket Programming
Summary
In this lab, I was able to gain hands-on experience with UDP socket programming and simulating real-world network impairments (loss rate). I learned the key differences between UDP and TCP, which are mainly that UDP is a connectionless and unreliable protocol that does not guarantee packet delivery or ordering. Furthermore, UDP does not need connection setup using listen() and accept() and instead uses a single UDP socket which can both send and receive data using sendto() and recvfrom(). In this lab I implemented UDP socket operations which included creating sockets with SOCK_DGRAM, binding sockets to local addresses to receive packets, and forwarding packets to specific destinations without establishing a persistent connection like TCP.
I also learned how UDP being stateless enables simple packet-forwarding, where a single program can function as both the receiver and the forwarder using only one socket. I know we were asked to implement packet loss to simulate real-life situations using random number generation. This allowed packets to be dropped to mirror congestion or unreliable links. 
Exercise Answers
Exercise 1: Effect of Increasing Loss Rate on Video Quality
As the loss rate increases, video quality gets worse and worse progressively.
Even at low loss rates 0-20, the video appears like it is lagging slightly. Occasional dropped packets cause brief, noticeable glitches.
At moderate loss rates 20-100, the video quality becomes noticeably worse. More frequent glitches show up, including occasional frame freezing and brief skips in the playback. 
At high loss rates 100-500, the video becomes severely degraded and barely watchable. Frequent freezing takes place as the player waits for the key frames.
At very high loss rates 500-1000, the video is basically unwatchable. The player repeatedly buffers and it is extremely hard to tell what is going on. 
The impact of the packet loss on video is non-linear because video codecs rely on temporal and spatial compression. A single lost keyframe ends up corrupting many upcoming frames until the next keyframe arrives.
Exercise 2: Should We Use TCP Instead of UDP for Multimedia? 
I disagree that TCP should be used instead of UDP for multimedia communication, particularly for real-time streaming. The main reason why is due to buffer space, retransmission time and jitter.
While TCP gives us reliable, ordered delivery by buffering the out-of-order packets until all the previous packets arrive. In multimedia streaming, this approach creates variable delays (jitter) as the receiving end is waiting on the retransmitted packets. For example, if packet 50 is lost, packets 51-100 sit in TCP's buffer and wait, which causes unpredictable delays. Real-time applications need consistent timing more than they need perfect reliability. UDP on the other hand allows for packets to be processed immediately once they arrive, which maintains a more predictable timing for playback.
Additionally, TCP automatically retransmits lost packets, which definitely sounds more beneficial. However, when it comes to real-time streaming, retransmitted data comes in too late to be useful. If a video frame needed at time 1s is lost and retransmitted at 5s, it might not arrive until the time by which point the player has already moved past that frame. The retransmitted data becomes useless, wasting bandwidth. UDP avoids this wasted effort by not retransmitting, allowing the application to skip damaged frames altogether.
